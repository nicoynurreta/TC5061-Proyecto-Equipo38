## Entregas del proyecto

El proyecto responde tres preguntas sobre la operación de MiBici con un modelo de regresión, uno de clasificación y uno de *clustering*. La primera entrega dejó la base: ingesta reproducible y versionada de los viajes, módulo de *features*, experimento base en MLflow y flujo de trabajo con ramas y *Pull Requests*. La segunda entrega convierte el repositorio en un [MLflow Project](https://mlflow.org/docs/latest/ml/projects/) que se ejecuta con un solo comando, compara varias candidatas por pregunta contra ese experimento base (con una búsqueda de hiperparámetros organizada como *nested runs*), guarda en cada corrida los artefactos que respaldan su resultado y deja el mejor modelo de cada pregunta registrado y en producción en el [Model Registry](https://mlflow.org/docs/latest/ml/model-registry/). La tercera entrega agrega la capa de calidad del repositorio: pruebas unitarias con pytest para cada módulo, con casos límite y una prueba de reproducibilidad del entrenamiento, validación de los datos con DeepChecks, chequeos de seguridad con su evidencia y un solo comando, `make verificar`, que corre todo. La cuarta entrega despliega el modelo en producción de P2 como un servicio REST con FastAPI y Pydantic, cargado por nombre y alias desde el Model Registry y empaquetado en una imagen OCI con `Containerfile`, con sus pruebas, las capturas del contenedor respondiendo y la documentación para construir la imagen, levantar el contenedor y consumir la API (sección Servicio de predicción). La quinta entrega vigila ese modelo en producción: compara con Evidently los datos de su entrenamiento contra los de 2026, mide su desempeño mes a mes, registra una versión reentrenada, decide entre las dos con un *A/B testing* de regla escrita de antemano y propone cuándo reentrenar (sección Monitoreo y drift). La sexta entrega convierte ese servicio en un sistema que se opera: `docker-compose.yml` levanta el servidor de MLflow y el servicio de predicción con un solo comando, un *pipeline* de GitHub Actions corre las pruebas, construye la imagen, levanta el sistema y lo prueba en cada *push* y en cada *Pull Request*, una prueba de carga con Locust mide hasta dónde aguanta mientras `docker stats` registra lo que consume, y un módulo calcula con esas mediciones el costo por inferencia (sección Operación del sistema).

La entrega final integra todo lo anterior, agrega el [Model Card](../MODEL_CARD.md) y reescribe el README como presentación general del proyecto.
